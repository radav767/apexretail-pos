# Phase 11 transaction, replay and disconnected-operation policy

Development policy established before guard changes, continuing from 9656d1a. This is a tested implementation target, not production approval or a change to legacy commercial pricing. Super Admin remains NO-GO.

| Request class | Authorization and license decision | Effects |
| --- | --- | --- |
| Historical sales, financial reports, receipt/fiscal evidence and committed-command recovery | Current authenticated identity, current tenant/branch/register and domain permission checks remain mandatory. Expiry, suspension or a later module downgrade alone must not hide existing business records. | Return existing records. Explicit receipt audit/delivery and reviewed acknowledgement may persist their existing document identity; no new sale, stock movement, payment or fiscal transaction. |

Only then bypass current write-license/module checks. | Return original result; do not rerun stock, price, tax, credit, approval, payment or delivery effects. A duplicate command never becomes a new transaction. |

## Decision and transaction boundaries

License authorization is a fresh server read at the new-command decision point. A later expiry/suspension does not cancel a command already authorized in flight; subsequent new commands observe the new state. This is an explicit linearization policy, not a claim of immediate cancellation across concurrent requests. A wall-clock timestamp supplied by a browser does not prove that a queue was licensed when captured.

Serialize equal command identities before checking receipts; persist fingerprint/result bindings in the SAME transaction as stock/payment effects. Do not allow helper-level commits to release command locks midway. Canonical fingerprints include business input and capture time; transient bearer/device/manager-approval credentials are not stored. Scope bindings and current credential checks remain independent of the fingerprint. Different actors, changed quantities/tenders/currency/discounts or a reused identity without proof fail closed. Generated UUID identities remain globally unique where the existing sales schema requires it.

Historic price/tax/customer/shift changes do not cause an exact committed command to be executed again. Return a verified committed receipt before attempting current-shift/price/credit revalidation, while still enforcing current actor/tenant/branch/register access. Active but expired accounts may retrieve evidence; inactive/deleted/revoked identities are not re-enabled by this exception.

## Shift and drawer decisions (established before shift guard changes)

Opening a new shift and recording a new manual drawer cash-in/cash-out are new business/financial writes and require a current server write license. A committed retry must match its complete original opening floats/note or drawer amount/currency/type/reason, original actor and register assignment; it returns the original result without another shift or drawer entry. A reused command identity against another shift conflicts. Transient manager-approval credentials are not request content and cannot be re-consumed just to acknowledge an existing effect. Existing tip-generated drawer entries remain bound to their tip receipt; the `tip:` idempotency namespace is reserved and cannot be submitted as a new manual drawer command. Legacy incomplete proofs permit historical GET, not reconstructed POST acknowledgement.

Closing an existing shift, including authorized manager exceptional closure, remains possible after license expiry/suspension: it freezes existing cash counts, variances, totals and report evidence. It must not add a sale, payment, stock or drawer movement. Every existing cashier/register, manager permission, branch, confirmation and exceptional-reason requirement remains. Exact closure retry must match complete counts/note/reason/confirmation plus original closing actor/context; changed counts with the same key must conflict instead of silently returning an unrelated closure. Historical shift/Z-report reads and existing report reprint accounting keep their scope/security policy. Session revocation still denies all of these operations. This closure exception is not permission to upload pending sales after expiry or post new cash movements on a closed shift.

## Bounded offline trust target

Implemented browser policy: at most **four hours from the last fresh online proof**, capped further by the signed snapshot expiry, grace and key deadline. Each authenticated subscription refresh signs a new random document challenge and current server iat. An older signed token cannot establish a new lease simply by replaying storage. Accept only the latest pending challenge within 60 seconds. Use signed server time plus the greater of monotonic/wall elapsed time; fail closed on monotonic reset, unexplained drift/rollback beyond 60 seconds, missing anchor or elapsed lease. Small tolerated wall adjustments cannot extend monotonic expiry. Clock state remains memory-only: reload/reboot, lost document state, changed company/cashier/register credentials and explicit logout require reconnect. Cross-tab logout broadcasts and auth-storage changes retire other open document leases. Cached local PIN/permissions alone never establish a lease.

New native sale-queue insertion and unpaid restaurant draft/kitchen/KDS capture require this lease. Existing records, command IDs, offline-shift attribution and synchronization/recovery remain intact; synchronization still applies current server policy to new work and exact proof checks to committed replay. Refresh while connected every 15 minutes, on visibility/reconnect and current cashier credential changes. The clock is checked at capture; periodic UI checking may show a warning up to 30 seconds later. Temporary network failures can use only an already valid lease for the same context; a signed suspension or online authorization rejection retires it. Backend verification on each authenticated online request continues independently.

Maximum disconnected revocation exposure is the remaining lease (at most four hours), not zero. A device owner can modify browser code/storage/clock APIs, so this is not hardware attestation or absolute anti-tamper protection. Browser/Android WebView lifecycle and hardware acceptance remain release gates. An online authentication request authorized just before revocation may finish; an old-epoch PIN result cannot become valid after logout. Server logout failure leaves the user signed out locally, with server revocation explicitly unconfirmed. Rollback cannot replace these checks with wall-clock-only cache restoration.

Signed entitlement maximum lifetime/grace remains an upper bound, never an extension after suspension. Browser-owned storage and wall clock are not tamper-resistant. Require a verified signed server-time anchor, bounded elapsed-time lease and reconnect on rollback, unexplained restart/anchor loss or lease expiry; never erase queued records. A disconnected device cannot learn immediate revocation. Production acceptance must state the maximum disconnected exposure and native/device trust assumptions rather than claim absolute clock/revocation resistance.

New queue upload after reconnect uses the current server write decision above. Existing offline-shift proofs continue to establish immutable attribution only. Closed shifts, moved/decommissioned registers and stale assignments retain their existing manager-review requirements. A rejected queue is not a failed committed transaction and must not be automatically discarded or charged again.

## Rollback

Any compatible application rollback must preserve user/session/employee revocation, canonical receipt matching, single-use credential/grant checks and queue retention. Never restore an older database over later sales, payments, acknowledgements or revocations. Additive migration downgrade must refuse to discard replay/revocation evidence; forward recovery is the default. No deployment or production migration is authorized.
