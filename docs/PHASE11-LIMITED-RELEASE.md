# Limited POS + Backoffice release contract

Updated28 November 2026 UTC; current evidence: [P0 checkpoint](PHASE11-RELEASE-P0-STATUS-2026-11-28.md). This contract supersedes blanket production deployment prohibitions for this limited release only. The user authorizes deployment **after all critical gates pass**. It does not authorize real provider transactions/messages/payouts, APK publication, credential/signing changes, destructive recovery or Super Admin opening. Optional Phase 11 expansion stops. Current decision: **HOLD; no production deployment performed**.

## Finite scope

Release the existing business POS and Backoffice with reconciled runtime/security fixes and supported ordinary selling: online single-method sales, permitted existing credit/collections/refunds, original receipt/history/recovery, shifts/cash, stock lookup, customer selection/quick creation, enabled existing business selling, minimal device settings and secure Backoffice handoff. Retain bounded offline leases and original durable queues; never erase or relabel a rejected/quarantined request. Preserve existing subscription terms, commercial limits and provider configuration; no fabricated renewal or grace extension.

Backoffice owns catalogue, employees, business configuration, ordinary stock/procurement/count workflows, historical reporting/read-only reconciliation exports and supported document preview/download. Preserve its approved ten settings sections, original leaf URLs, permissions, values, browser history and operational recovery. Operational workflows remain operational. Existing source-supported workflows still require the exact configuration and supported business/device matrix below; inclusion is not certification of every business type or optional feature.

No new recipes, dispatch, airtime/vouchers, vendor accounting sync, live fiscal/payment QR, automated receipt/email/WhatsApp delivery, new printer bridge, new official artwork or platform console. Existing uncommissioned surfaces must remain disabled or explicitly unavailable. Software printing/PDF preview is not physical printer/device acceptance. Existing native printer use requires separate evidence for the actual supported installed device/transport; no new APK is in this release.

Freeze these server modes explicitly: `APP_ENV=production`, `SPLIT_CHECKOUT_MODE=disabled`, `QUOTATION_PRICING_MODE=disabled`, `BUSINESS_EMAIL_MODE=disabled`, `DOCUMENT_DELIVERY_MODE=disabled`. The current implementation supports sink delivery only in test; password recovery must visibly say unavailable in this release. Preserve existing reset consumption/revocation logic, including when UI is hidden. Test-only split and saved-pricing paths remain test-only; changing environment to enable them is prohibited. Unsupported repeated effective quotation positions, non-two-decimal base currencies and collected-credit payouts remain gated. Preserve historical foreign-currency precision/rates/refund residuals; no currency data rewrite.

New external integrations cannot become a release dependency. Do not disable an existing commissioned production business flow silently: inventory its existing entitlement/configuration, determine compatibility and qualify it, or explicitly exclude that business/device from the release before deployment. Business-specific pharmacy forms/expiry/disposal and actual printer/device combinations are not qualified by a Retail-only journey.

## Super Admin dependency boundary

The POS/Backoffice runtime does **not** need the Super Admin web console to be open or commissioned for normal authenticated business requests. It does depend on shared subscription/commercial models, entitlement signing/verification keys, current subscription state, device limits, security epochs/revocations and migration/schema compatibility. `subscriptions/service.py` reads shared `PlatformSetting` trial policy and commercial services; existing subscription renewal/billing paths still require their actual policy/provider/authorized administration. Do not replace that dependency with owner shortcuts, fake paid status, public platform endpoints or disabled enforcement.

Keep `admin.apexpos.cloud` holding503 and platform MFA/role/recovery restrictions. Console-specific UI, two-role console commissioning and optional platform features are deferred. **Business** backup/key custody/independent restore, database migration privilege boundaries, runtime/config compatibility, tenant isolation, secure sessions and preservation of newer evidence remain release gates. Running the installed API as UID0 is an observed existing security exposure, not accepted merely by deferring the console. Review and resolve its release disposition through the protected deployment/runtime workflow; do not silently change service identity or expose secrets.

## Deployment and recovery plan to finalize before production

1. Capture candidate commit, tracked-source manifest, Python/runtime/document locks, vetted wheel hashes, Node/npm versions, both final dist file hashes, public entitlement-ring hash, additive migration order and feature/config presence manifest. Protect private configuration; do not commit secrets, reset grants, cookies or production business data.
2. Review existing `ops/phase10` protected owner/worker pattern, not its obsolete revision pins. Prepare Phase11 plan with exact observed start/head and manifest verification. Abort on unexpected schema, source/config drift, missing proof, hash mismatch, permission/tenant failure or unhealthy baseline.
3. Before maintenance, obtain bounded genuine operator clearance for sales/write pause, registered device/queue state and open shifts. Retain every offline command and its original context, proof and acknowledgement. Do not manufacture `offline_queues_clear=true`; if nonempty queues are supported, test the explicit preservation/replay protocol and revise the reviewed gate rather than lie to the old runner.
4. Use the established deployment lock and stop/fence only authorized application writers/watchdogs during the approved interval. Take verified consistent backup and original-column/financial/stock/revocation controls. Preserve current static assets and existing service/config identities. Run additive migrations via the protected owner workflow; do not migrate through ordinary app credentials.
5. Switch only verified backend/artifact paths; restore authorized services through the reviewed workflow. Verify health/readiness/schema, business login/PIN/refresh/handoff/permission denial, historical receipts/finance/stock and queue recovery without real provider messages/transactions. No synthetic sale in production without a separately approved nonbusiness fixture policy.
6. Recovery triggers: failed health or sign-in, tenant/role leak, revoked token accepted, ledger/stock mismatch, queue loss/rebinding, duplicate effects or corrupt immutable outputs. Fence new writes, retain diagnostics and newest data, deploy a compatible forward fix retaining new schema/session epochs/revocations/command parsers. Asset rollback is permitted only when compatible with new APIs/proofs and retained browser caches. Never downgrade these security tables/guards or restore an old backup over newer sales. Restore to a separate database for diagnosis; reconcile and validate before any separately reviewed cutover.

This is a reviewable plan, **not a run receipt**. Final commands/hashes, interrupted-deploy evidence, production backup/control receipt and health/recovery timings remain required before touching production.
