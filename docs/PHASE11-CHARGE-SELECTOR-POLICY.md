# Shared charge-product selector contract — 26 November 2026

Before implementation: extend existing read-only selection with allowlisted `purpose=general|charge` and optional exact `selected_id`. General catalog/branch permission and behavior remain. Charge purpose requires current business-settings authority and authorized tenant/branch/register; it permits the same profile configuration metadata as existing business options, including actors whose business-settings permission does not grant general catalogue access. Direct service reads require current identity, role, epoch and scope rather than relying solely on route dependencies. Historical expiry alone cannot hide existing configuration.

Eligible charge products must belong to the tenant, be active/not deleted, have `product_type` service or non_stock and explicitly not track inventory. Apply the predicate to both count and rows; server pagination, name/SKU/barcode search and exact selected-ID lookup never return ineligible/foreign data or costs. Literal wildcard escaping and bounded query/page sizes remain. Selected-ID lookup allows saved associations beyond the old1000-option cap to disclose their current authorized source name; no fake selectable result is created when unavailable.

Adopt in profile tip/service fields using the shared selector and optional explicit clear action, preserving current business type and existing profile values. Optional fields may be cleared without fabricating a product. Ineligible/currently unavailable selections are visible as needing review; final profile service must independently refresh and share-lock eligible products in deterministic ID order through commit. The validation decision linearizes there; later catalog changes remain possible and must be checked by later domain operations. A search result is not permission, approval or a price/tax override. No new financial formula, payout, stock deduction or provider action.

Retain current revocation checks and require the existing write license/permission for configuration saves. Existing profile PUT is unversioned configuration, not a new immutable command protocol or lost-response acknowledgement; reload reads current settings. Do not claim it offers quotation/stock command recovery. Concurrent catalog changes and stale cached ORM objects must not bypass final eligibility. No recipe/component or inactive-product management scope is added; those need separate permissions/filters and acceptance.

Independent connections must show catalog-writer-first rejection and profile-validator-first product lock ownership through commit. Use real POS/Backoffice shells and synthetic persistence; software selector evidence is not provider/payment/tip-payout/physical-device acceptance. Preserve all existing identity/revocation/lease/offline queue/transaction/stock cutoff/cancellation/tender/refund/document/consent evidence. All unsupported posting/recipe/repeated-position/base-precision/payout and Production/Super Admin NO-GO gates remain.
