# Advanced catalogue selector boundaries — 26 November 2026

Define these boundaries before expanding the shared selector. POS remains daily selling and stock lookup under the superseding navigation contract; catalogue administration belongs in Backoffice. No selector supplies posting authority or guarantees that a later catalogue write cannot change eligibility.

An unavailable saved choice remains evidence for review; search must not erase its ID, invent a replacement or mutate an immutable sale/quotation/document. General exact lookup does not reveal inactive, deleted or foreign records. Unknown purposes fail closed both at the HTTP schema and direct service. Read results never reserve stock or authorize a payment; final transaction services retain their original policy, locks and proofs.

Offset pages retain their existing non-snapshot limitation under concurrent catalogue changes. No adoption beyond the tested variant/price-level management subset, bulk catalogue rewrite, recipe enablement, new financial rounding or posting capability is authorized by this policy. Existing supported catalogue APIs remain in Backoffice, with their permissions/data preserved. Production and Super Admin remain NO-GO.

## Dedicated management contract before acceptance — 27 November 2026

Add only explicit management reads with product-selection-management-v1 metadata and active/inactive/all status. Existing general/charge requests retain active-only defaults; passing their inactive/all status is rejected rather than silently exposing archived rows. Management requires a current owner/administrator business User and products_edit; any employee/POS session is denied even with owner role or edit flags. Tenant, active branch, current user epoch and selected-ID scope remain enforced at HTTP and direct service. No costs or deleted products are returned. Rows include explicit active state, bounded search/pages and exact selected-ID lookup.

Initial UI adoption is Backoffice variant and price-level configuration only, with explicit branch and state controls. Existing unit/composite/component forms remain separate; no recipe selector or posting enablement. An unavailable selected ID is retained for review, not cleared/reactivated. Search never reserves stock; later catalogue state changes remain possible, and original mutation endpoints keep their own permissions/validation. Reads under concurrent updates have the existing read-committed pagination limit; they do not claim a frozen multi-page snapshot. Require direct API/service, POS denial, state/tenant/branch/revocation, current-source/stale response and real Backoffice shell acceptance before calling this implemented subset accepted.
