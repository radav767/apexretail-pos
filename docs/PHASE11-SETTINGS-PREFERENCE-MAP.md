## Incremental preference contract

Presentation is separate from financial, identity, terminal authority and operational mode. First bounded preference is shared product-search results presentation (`table` or `cards`). Company defaults may be overridden by an authorized branch, then an authorized device; absent keys inherit. No setting may hide safety notices, permissions, stock evidence or change posting/checkout/lease behavior. A read must resolve only the authenticated tenant and authorized branch/register. Writes require current business-settings permission, current write license and current epoch/register proof. Company defaults require owner/administrator. Each scope has one deterministic versioned projection and immutable workflow command acknowledgement; stale writes conflict, equal committed requests recover original result. Clearing a scope writes an empty override with a new version, never deletes its evidence. Device preferences bind branch and assignment revision so reassignment cannot carry an old branch's override.

Local user overrides, full light/dark/system themes, screen layout, checkout/customer-display modes and menu/button customization remain separate increments with accessibility/recovery acceptance. Do not describe the first selector preference as a complete POS theme/customization suite. Planned precedence if personal overrides are added: company → branch → device → per-actor local override, with explicit reset/inheritance and validated allowlisted values. Device authority and operational/payment modes never inherit from presentation settings. No arbitrary CSS/HTML, uploaded layout code or imported preference keys. Server defaults are persisted online; an unavailable preference read falls back to the table presentation. No offline mutation queue or lease authority is added.

Rollback/forward recovery must preserve all session/epoch revocation, leases, offline queues, command identities, cancellation/stock cutoffs, financial snapshots and immutable documents. No migration or production change is needed for a workflow-backed preference projection; prior workflow evidence triggers and append-only command acknowledgements remain active.
